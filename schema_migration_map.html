Ticket System Tech - data migration planning

Schema Migration Map

Full entity-relationship diagrams for both databases involved in the osTicket to Ticket System Tech migration: TicketSystemTech (the destination, SQL Server, currently empty) and supportimel_dbpodrska (the source - a live osTicket installation with real support history). Both run on the same local localhost\MSSQLSERVER01 instance.

Scope: each schema is grouped by domain rather than shown as one solid block, and framework/operational tables are left out — ASP.NET Identity plumbing (AspNetRoleClaims, AspNetUserTokens, …) on the Ticket System Tech side, and osTicket's session/log/search/plugin internals (ost_syslog, ost_session, ost__search, ost_lock, …) on the other — since neither holds data that migrates. Column types are simplified to their base SQL type; exact lengths are in the live schema.

Ticket System Tech

destination · SQL Server · empty

GUID primary keys throughout. The schema is intentionally slim compared to osTicket — one ticket table instead of ticket + cdata + thread + thread_entry, one Users table instead of user/user__cdata/user_email/user_account/staff.

supportimel_dbpodrska

source · osTicket · live data

Standard osTicket schema (ost_ prefix). Bigint IDs, no declared foreign keys anywhere in the database — every relationship below is inferred from osTicket's own column-naming convention (*_id), not enforced by SQL Server. Several core tables are split into a base table plus a __cdata 1:1 extension — that split doesn't need to survive the migration.
